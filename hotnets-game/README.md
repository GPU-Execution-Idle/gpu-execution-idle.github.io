# Wake the GPU! (one-button jump game)

A short timing game for the HotNets paper *“The Network Should Wake the GPU”*, replaying five
waits from a real LLM-serving trace. Space (or the single button) ramps the GPU's frequency up
once per wait; the GPU drops back to idle automatically after each request's work.

```
web/                  ← static site, no build step, no external requests (works offline)
  index.html, game.css, game.js   UI: three aligned rows (prediction, GPU work, GPU frequency) and results
  audio.js            background music and outcome sounds (Web Audio, synthesized)
  jump-model.js       playback state machine and the causal percentile prediction range
  sim.js              energy / delay model shared by every strategy
  data.js             GENERATED by tools/build_data.py from the experiment logs
tools/build_data.py   picks the segment and extracts it from ~/agent/... (local logs, not published)
tests/jump-model.test.mjs   node tests/jump-model.test.mjs   (Node 17+)
tests/sim.test.mjs          node tests/sim.test.mjs
```

## Run locally

```bash
python3 -m http.server 8765 --bind 127.0.0.1 --directory web
# then open http://localhost:8765/ (forward port 8765 when working on a remote machine)
```

Published at `/hotnets26-game/` (root `projects.json`, `"source": "hotnets-game/web"`). The deploy workflow
runs both test files before building the site.

## How it reads

- **Network prediction:** a purple range bracket: previous arrival + the middle 40% (30th–70th
  percentile) of the latest 16 observed inter-arrival intervals, about 4 s wide here. The bracket
  starts one wake latency (0.32 s) plus a 0.5 s reaction allowance before the earliest predicted
  arrival, so a press within 0.5 s of its start is always in time for arrivals inside the range (tested). Only past arrivals are used. The algorithm is stated in the game's folded "How to read the game".
- **Work:** after a request actually arrives, a line rises from the start of its work (solid dark
  block) into the prediction row. Work always starts at arrival; after a late wake its first part is
  hatched amber ("Slow down at reduced frequency!"), so the block is longer: it spans the request's
  added latency at the scene's scale (trace delay / wait speed); its label stays up through the work.
- **Rows:** prediction, work and frequency are about the same height. The frequency row, which the
  player controls, has a blue tint and edge and a "you control" tag.
- **GPU frequency:** black by default; red while it waits at high frequency, amber while late work
  runs at reduced frequency, gray while it ramps down. Every ramp, in time or late, takes 1.1 s of
  real time in slow motion (the whole scene slows), so all wakes draw the same slope.
- **Outcomes** (one per request, `jump-model.js`): ⭐ "Perfect timing!" (in time, at most `PERFECT_SCREEN_S`,
  0.5 s on screen at high frequency; a ring and sparkles burst from the GPU marker, text only with reduced
  motion), 👍 "Good timing!" (at most `GOOD_SCREEN_S`, 1.5 s; a smaller pop), 🔥 "Too early!" (waiting longer than that), ⏰ "Too late!" (arrived before the wake finished).
- **Sound** (`audio.js`): Web Audio, no files. Soft background music, a jump sound on the wake press and one cue per outcome; off by
  default; the music-note button turns it on (blue) or off (grey), remembered in this browser.
- Past and future have slightly different backgrounds. One pause after the first request. Replay
  speed is adjusted (waits 1.4× faster for the first request and 3× for the rest, `waitSpeed`, so a run takes about 12 s + 30 s; the 0.32 s wake ramp plays as a 1.1 s slow motion of the whole scene, and the work is slowed for visibility);
  results use the original timings.
- **Results:** energy as −x% vs. always-high frequency; latency penalty as +y%, the added delay
  normalized by the five requests' latency at full frequency.

## Data (`tools/build_data.py`)

- **Trace:** Azure LLM inference trace (code), partition 0 of 8, from the 100-request replay on
  Qwen3-14B / vLLM / L40S (`~/agent/interface_log/20260713_220300`).
- **Segment rule:** the shortest five-wait window whose arrivals **all fall inside their predicted
  range**, at varied positions within it (std. dev. of position ≥ 0.25, so no fixed press timing always
  wins), and where every request still leaves ≥ 2 s idle before the next arrival after its run time
  plus late-wake slowdown. This picks requests 44–49. The rule makes this excerpt much friendlier to the
  predictor than the trace as a whole: across the full trace, 28 of 83 arrivals (34%) fall inside their
  range. The game's "How to read" section states this.
- **Measured:** arrival times and the 16 preceding arrivals; each request's run time at full clocks
  (`no_scaling`); each request's slowdown when woken reactively (`scale_sm_memory` vs `no_scaling`,
  matched by trace row); power levels (median NVML power, normalized to high-clock idle = 1).
- **Reused:** the 0.32 s SM+memory wake lead from `hotnets-artifact/web/shared/params.js`.
- **Modeled (`sim.js`):** energy and delay per strategy. Downclocking is instant and free; a wake at
  least one wake lead ahead adds no delay; a shorter lead scales the measured slowdown linearly;
  slowdown time (work running while clocks are still low) is charged at low power. Every strategy is
  compared over the same window, ending when the slowest possible run ends. As a result, waking on
  arrival is always the most energy-saving strategy and only costs latency, as in the measured runs.

## Tests

`node tests/jump-model.test.mjs` covers the causal percentile range (including that every segment
arrival lies inside its range and that changing future arrivals does not change a prediction), the
16-interval cap, ramp and single press, persistent prediction history, work duration, the single
pause, late and partial wakes, results and replay.
